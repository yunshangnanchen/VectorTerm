# 拖动缩放抖动:为什么修了四轮还没好,以及和 wezterm / ghostty / kitty 的架构差异

> 基线提交 `228ae31`。**本文只做分析,不含任何代码改动。**
> 文中引用的 winit / wezterm / ghostty / kitty 行为均已对照源码或官方文档核实;
> 引用的毫秒数字来自本机实测(`VECTORTERM_TRACE_RESIZE=1` + 高速抓帧)。

---

## 0. 结论先行

两句话:

1. **不是 bug 没找到,是"要优化什么"定义错了。** 四轮都在缩短"帧迟到的毫秒数"(8.2 → 6.5 → 5.2 → 1.0ms),而观感只取决于一件事:窗口变大的那一拍里,屏幕上有没有新尺寸的像素。这件事由 DWM 的合成节拍决定,**不由我们的毫秒数决定**。
2. **成熟终端不是把这一帧做得更快,而是让这一帧不需要新排版。** kitty 把这个答案直接写进了配置项文档:`resize_draw_strategy static`(拖动中"画当前内容,基本不变")+ `resize_debounce_time 0.1`(等 100ms 没有新 resize 才通知程序重排)。它根本不去追那一帧。

一句话概括三家与我们:

| | 它修的是什么 |
|---|---|
| wezterm | 修**时序**:自己拥有消息循环,把"改尺寸"和"出示新帧"压进同一个消息周期 |
| ghostty | 修**线程**:排版和出帧搬出窗口线程,窗口线程永远不被阻塞 |
| kitty | 修**需求**:拖动期间干脆不重排,问题不存在 |
| VectorTerm(本项目) | 修**毫秒** —— 而毫秒是三家里唯一没人去修的量 |

## 1. 把"抖"换算成一个可判定的量

观感只由一个量决定:

```text
T = t(新尺寸的像素真正上屏) − t(窗口矩形变成新尺寸)
```

- `T` 落在同一次 DWM 合成里 → 看不见。
- `T` 跨过一次合成 → DWM 把**上一帧的旧尺寸表面按比例拉伸**铺满新客户区,肉眼就是"拉长一下再弹回"。拉伸比例 = 新宽/旧宽。

这个定义顺带解释了一条此前的关键线索:**只有拖右边/下边抖,拖左边/上边基本没有**。拖右/下时窗口原点不动,DWM 就地拉伸旧表面;拖左/上时窗口位置同时在变,DWM 走的是"移动 + 重画"的另一条路径,拉伸不明显。

**要命的地方在于:这个量,四轮里一次都没有直接测过。** 我们测的是 `EV_RESIZED → present 返回`,它只是 `T` 的一个下界。而在 flip 模型下,present 返回 = 把 buffer 交给 DXGI,**不等于进了合成器**。

## 2. 四轮时间线:每轮都做对了什么,漏了什么

| 轮 | 提交 | 当时的假设 | 实际改到 | 收益 | 为什么不够 |
|---|---|---|---|---|---|
| 1 | `5c47ecc` / `5566d6a` | 抖动来自 PTY / PSReadLine 重绘 | 拖动期间冻结网格同步 | 排除了内容层最大的噪声源 | 假设错层,但**方向不完全错**:SIGWINCH 引发的 shell 重绘确实是放大器(见 §5)。冻结让内容与窗口脱节,松手还要跳一次 |
| 2 | `afa9cbc` | 内容没跟上窗口尺寸 | 恢复 realtime,格子一变立刻提交 | 消除"窗口变了、行列数没变"的脱节 | 把**整屏 reflow** 放进了关键路径,每帧成本上升 |
| 3 | `93774a8` | 呈现排队导致旧帧被拉伸 | `Resized` 里同步 `redraw + present` | 8.2ms → 6.5ms,压掉了消息泵空转 | `Surface::configure`(DXGI `ResizeBuffers`)仍在新帧第一步,正好压在"窗口已变大、新帧未上屏"的空档里 |
| 4 | `228ae31` | `ResizeBuffers` 落在空档里 | `WM_SIZING` 里提前配交换链 | 6.5ms → 0.8~1.4ms,`WM_SIZE` 里的重配置归零 | 应用侧已经到 1ms,但 vsync 量化 + "帧内容依赖新布局"两条没动 |

四轮把应用侧从 **8.2ms 压到 1.0ms,是 8 倍**。但观感的统计对象不是均值,是**尾部**:

- 一次拖动会产生几十到上百次尺寸变化。
- 只要其中 2~5% 的帧跨过了合成拍,**全程看上去就是"一直在抖"**。
- 8ms → 1ms 改善的是"坏帧的比例",不是"是否存在坏帧"。而人眼对"每两秒闪一次"和"每半秒闪一次"的评价几乎一样:都叫抖。

这就是第三轮之后"指标大胜、观感没变"的原因。

## 3. 为什么四轮都收不了尾

按"代价"排序,五个原因。前两个是技术性的,后三个是方法论的。

### 3.1 现象词太粗:一个"抖"对应三种不同的物理事件

| 物理事件 | 表现 | 属于哪层 | 修它的轮次 |
|---|---|---|---|
| 重排滞后(内容按旧列数画) | 文字位置不跟窗口走,松手跳一次 | 内容层 | 1、2 |
| 旧帧被合成器按比例拉伸 | 文字横向拉长再弹回 | 呈现层 | 3、4 |
| 整格吸附导致的位移跳变 | 每跨一格,长行折行点整体前移一格 | 几何层 | **四轮都没处理** |

三者都会被人称作"抖",而且**互相遮蔽**:最大的那一项消失后,原本被淹没的那项才浮现出来。所以"还是一样"是诚实的反馈 —— 观感确实一样,只是成分换了。

第三条至今仍在:开着 `use_resize_increments` 时,一次 120px 的拖动会让内容按整格跳十几次,每次位移 8~9px。这个"跳"和"拉伸"在余光里长得几乎一样。

### 3.2 指标选错了对象

优化的是 `EV_RESIZED → present 返回` 的**均值**,感知的是"新尺寸像素上屏"的**尾部**。两个量的相关性只有一半:前者能压到 1ms,后者的下界仍然是"到下一个 DWM 合成拍"。

结果就是一个很危险的局面:**任何在这个指标上变好的改动,都自动显得"应该有效"**,哪怕观感毫无变化。第三轮之后正是这样。

### 3.3 度量工具本身坏了两轮

`tools/diagnostics/verify_stretch_fast.py` 的亮度公式用 `int16` 计算 `255*150`,溢出后亮部变负数,长时间判成 "NO BASELINE"。也就是说,中间有若干轮"抓帧 0% 拉伸"的结论是**假阴性**。

工具错的时候,"验证通过"比没有验证更危险 —— 它会让一个方向提前被判定为完成。

### 3.4 架构天花板被当成"再优化一点"

有三条硬约束,前两条决定"再快也可能有残差",第三条决定"残差必然存在":

1. **surface 尺寸必须等于客户区尺寸**(DXGI flip 模型的硬要求)。不等,DWM 就拉伸。所以"避免拉伸"和"避免 ResizeBuffers"是同一件事的两面。
2. **present 的时间被 vsync 量化**。0.2ms 和 1.4ms 在没赶上当前合成拍时,观感完全一样。
3. **一帧的内容 = f(新窗口尺寸)**。因为每帧都要用新行列数重新排版整屏文字,"正确尺寸的帧"天生是链路上最慢的生产者。

四轮全部在跟第 1 条的**代价**搏斗(把 ResizeBuffers 挪早),没有一轮去动第 3 条 —— 而第 3 条才是"这一帧为什么必须迟到"的原因。

### 3.5 反馈环太长,而且抽象层要打洞

改 Rust → 编译 → 重启 → 手拖 → 肉眼判断。每轮只有 1 bit 信息,现象还依赖 DPI、驱动、是否最大化、鼠标速度、当时有没有输出流。

再加上 winit 把关键控制点藏在抽象层后面:`WM_PAINT` 只派发事件后交 `DefWindowProcW`、`WM_ENTERSIZEMOVE` 完全不暴露。每修一层都要用 `SetWindowLongPtrW` 往窗口过程里打洞,而打洞本身引入新风险(裸指针生命周期、重入、矩形预测失准)。**每轮的实现成本在递增,收益在递减。**

## 4. 三个参照实现,各自把问题放在了哪一层

### 4.1 wezterm:自己就是窗口过程

- Windows 上是**原生 win32 窗口**,自己实现 wndproc(不是借用框架)。
- `wm_size()` 里**同步** `dispatch(WindowEvent::Resized)`,紧接着 `wm_paint()`;`in_size_move` 为真时还会 `SPAWN_QUEUE.run()`,把排队的异步 paint 任务当场跑掉。
- 它也 reflow(和我们一样,`apply_dimensions()` 触发整屏重排),区别是:**"改尺寸"和"出示新帧"在同一个窗口消息里完成**,不需要跨过消息泵的一轮,也不需要等主循环回来。

→ 它修的是**时序**,而且因为它拥有消息循环,所以修得动。

### 4.2 ghostty:排版在另一条线程上

- 平台:macOS(AppKit / SwiftUI)+ Linux(GTK4),**Windows 官方仍是"计划中"**。
- 每个终端 surface 一条**独立 renderer 线程**(`src/renderer/Thread.zig`),加上独立的 IO 线程;主线程、IO 线程、渲染线程三分。
- 渲染线程有自己的事件循环(`xev`)和帧定时器(`render_h` / `draw_h`),还有一个 **`draw_now` 异步句柄可以强制立刻出一帧**。resize 也只是 mailbox 里的一条消息:`resize`("Screen size or padding changed")。
- 关键差异:**窗口线程从不做排版,也不做 present。** 窗口尺寸一变,主线程只更新 surface 尺寸、发一条消息;建帧、上传、present 全在渲染线程。窗口线程因此永远不阻塞,下一个 resize 永远进得来。
- 1.3 版起用 damage tracking,官方 release notes 原话:"the renderer holds the terminal lock 2x to 5x less per frame. And in most frames, the renderer doesn't hold the lock at all."
- 1.4 版把 Linux 侧改成 EGL 自绘线程 + DMABUF 交给 GTK,三缓冲,主线程不再有 GL 调用。

→ 它修的是**线程**:把"迟到"这件事从窗口消息路径上彻底摘出去。

### 4.3 kitty:拖动中不重排

- Python 主循环 + C 扩展;窗口层是 GLFW;**渲染在主线程**(单线程),PTY 交互在独立 I/O 线程。
- 它的取舍最直接,而且写在配置文档里:

| 配置项 | 默认 | 含义 |
|---|---|---|
| `resize_draw_strategy` | `static` | 拖动进行中**画当前内容,基本不变**。另有 `scale`(就是"我要那个拉伸")/ `blank` / `size` |
| `resize_debounce_time` | `0.1` | 等 100ms 没有新的 resize 事件,**才**通知程序 resize + redraw;macOS 因为系统给 live resize 的起止事件,松手立刻重排 |
| `repaint_delay` | `10`(ms) | 渲染循环里人为引入的节流,省电用 |
| `sync_to_monitor` | `yes` | 跟垂直同步 |

- 效果:拖动全程文字的**形状不变**,只是窗口在变大、右下留白;松手 100ms 后一次性重排。
- 它也有增量:字形缓存在显存里,`screen->is_dirty` 标志做延迟渲染,一帧通常只往 GPU 传几个字节。

→ 它修的是**需求**:既然"新排版"会带来形变,那就在拖动期间不产生新排版。**问题被取消了,而不是被加速了。**

### 4.4 横向对比

| 维度 | wezterm | ghostty | kitty | VectorTerm(本项目) |
|---|---|---|---|---|
| 平台 | Win / mac / Linux | mac / Linux(Windows 计划中) | Linux / mac / BSD(**无原生 Windows**) | Windows |
| 窗口层 | 自绘 wndproc | AppKit / GTK 原生控件 | GLFW | winit 0.30(借来的消息循环) |
| 渲染线程 | GUI 线程 + 可泵任务队列 | **每 terminal 一条渲染线程** | 主线程 | 主线程(和消息循环同一条) |
| resize 中是否 reflow | 是 | 是,但在渲染线程侧 | **否**(`static` + 100ms 防抖) | **是,每次 `WM_SIZE` 都做,且在关键路径上** |
| 帧内容是否 = f(新尺寸) | 是 | 是 | **拖动中不是** | 是 |
| 脏区 / 增量 | 有 | 有(damage tracking) | 有(`is_dirty`) | **无,每帧全量重建** |
| 标签栏 | 同窗口自绘 | 原生控件 | 同窗口自绘(同一 GL 表面) | 同窗口自绘,**同一份显示列表 + 同一张 swapchain** |
| 呈现节奏 | 消息驱动 | 渲染线程自己的帧时钟 | `repaint_delay` 定时器 | 消息驱动 + vsync |
| 拖动状态判定 | `in_size_move`(系统消息) | 系统 resize 事件 | 系统 resize 事件 + 防抖 | `GetAsyncKeyState(VK_LBUTTON)` **猜** |

### 4.5 一个必须说清楚的限制:它们不必面对同一条路径

- **ghostty 和 kitty 都没有原生 Windows 版**,所以它们从来不需要面对 DWM 的"重定向表面按比例拉伸"。
- X11 下窗口变大只改变**裁剪区域**,合成器不会把上一帧放大;Wayland 下缩放发生在客户端提交的 buffer 与 surface 尺寸不匹配时,通常由下一帧修正。**Windows 的 DWM 则会主动拉伸旧表面** —— 这是平台语义差异,不是实现水平差异。
- macOS 的窗口服务器在 live resize 期间**同样会拉伸旧内容**(应用卡住时能看到整个窗口被放大),ghostty 正因此才要把出帧路径压到渲染线程上。

→ 结论:**不能把它们的"不抖"直接当作"我们的实现差"**。它们的架构里有一半优势来自平台,另一半(时序、线程、是否重排)才是真正可学的。

## 5. 我们的每一帧,到底做了什么

`redraw()` 的真实顺序(全部在窗口线程上):

```text
WindowEvent::Resized(WM_SIZE)
  ├ update_geometry → compute_grid                       <0.1ms
  ├ commit_grid → pty.resize + term.resize(整屏 reflow)   0.1ms + reflow 本身
  └ redraw_sync
      ├ term.lock() → snapshot(整屏拷贝)                  <0.1ms
      ├ build_frame(全量重建显示列表,无脏区)              <0.1ms
      ├ build_tab_bar(追加到同一份列表)
      └ gpu.draw:图集/实例上传 + submit + present          0.8~1.4ms(交换链已在 WM_SIZING 配好)
```

对照三家:

- **第 4、5 步在 ghostty 是另一条线程上的事**,窗口线程根本不参与。
- **第 3 步在 kitty 拖动期间直接不做**;第 5 步它有脏行,不做全量。
- **第 3 步和最后一步在 wezterm 是同一个消息里的连续动作**,中间不回到消息泵。

而我们的第 3 步有一层别人没有的连锁反应:

```text
pty.resize → ConPTY 改尺寸 → SIGWINCH → shell / PSReadLine 重绘
           → 产生新的输出 → 触发新的重绘 → 又要重新 snapshot + build
```

**拖动越猛,内容风暴越大**,这段耗时完全不受渲染层控制。第一轮把它误判成根因,其实它是**放大器** —— 它决定了"那一帧有多大",而架构决定了"那一帧有多晚"。

## 6. 四条硬约束(不改架构只能逼近,不能消除)

1. **surface 尺寸 == 客户区尺寸**。不等就被拉伸;要等就必须 `ResizeBuffers`。两者是同一件事。
2. **present 被 vsync 量化**。没赶上这一拍,前面省的全归零。
3. **帧内容 = f(新窗口尺寸)**。只要排版依赖尺寸,就永远存在"窗口已经变了、排版还没算完"的窗口期。
4. **标签栏和内容共用一张交换链**。所以"终端内容被拉伸"必然连带标签栏一起被拉伸 —— 这解释了那个独有症状:"连标签栏文字都在抖"。Windows Terminal 用 XAML 独立合成层规避,ghostty 用原生控件规避,kitty 靠"拖动中不重排"规避。我们三样都没有。

## 7. 如果继续做,按杠杆排序(本次均未实施)

| 选项 | 收益 | 代价 / 风险 | 参考对象 |
|---|---|---|---|
| **A. 拖动期间不重排** — 保持旧列数出帧,新区域留白;松手或静止 100ms 后一次性 `commit_grid` | 直接消除"新排版晚于窗口变化"这个前提,是唯一能让 `T` 与排版无关的做法 | 需要可靠的"拖动中"信号;拖动中右侧会短暂留白 | kitty 的 `static` + `resize_debounce_time` |
| **B. 拿 `WM_ENTERSIZEMOVE` / `EXITSIZEMOVE`** | A 的前置条件;顺便替掉 `GetAsyncKeyState` 猜法,三条策略不再选错 | 小,`winhook.rs` 已经在了,加两条消息 | wezterm 的 `in_size_move` |
| **C. 内容放进子窗口 / 独立合成层** | 父窗口 resize 只改裁剪、不改子窗口尺寸 → DWM 只裁不放,物理上不可能拉伸 | 大:输入、焦点、IME、DPI 都要重做 | Windows Terminal 的 XAML 岛 |
| **D. 标签栏独立图层** | 解决"连带被拉伸" | 中:第二张 swapchain 或 DirectComposition visual | — |
| **E. 换掉 winit 事件层,自绘窗口过程** | 和 wezterm 完全同构,拿到全部消息控制权 | 大,但 `winhook.rs` 已是雏形 | wezterm |
| **F. 度量补到"上屏"** | 没有它,后面每一步仍然只能靠肉眼验收 | 小:PresentMon 或 DWM ETW | — |

排序理由:**A 是唯一"把问题取消"的路,而且改动量最小**;C/E 是彻底方案但成本高;F 是所有后续工作的前提,否则又会重演"指标好了、观感没好"。

### 7.1 E 想买的东西,有四种买法

E 的动机是"要消息控制权",但这件事有四个价位,不必一步到位:

| 买法 | 换来了什么 | 换不来什么 | 代价 |
|---|---|---|---|
| **tao**(Tauri 的 winit fork) | 菜单 / 托盘 / 更贴桌面应用 | **消息级控制权——拿不到**,事件循环模型与 winit 同源 | 中(改调用点),收益≈0 |
| **复用 wezterm 的 `window` crate** | wezterm 的时序语义(原生 wndproc + `wm_size` 内同步 paint + `in_size_move` 泵队列),不用自己写 9k 行 | 仍然"帧内容 = f(尺寸)" | 依赖闭包:`config` / `wezterm-font` / `euclid` 等,要一起 vendor(我们已有 term/termwiz 等 9 个 crate,不是从零) |
| **`winsafe` 或直写 `windows` crate + 自建消息循环** | 全控制:自己的泵、`WM_ENTERSIZEMOVE`、同步 paint、多窗口共享渲染线程 | 同上 | 大:键盘规范化 2,229 行 + IME + DPI + 状态机,且只能人肉验 |
| **子 HWND(内容窗口)+ 父窗口只管裁剪** | **DWM 只裁不放,文本在物理上不可能被拉伸**;贵的活(reflow)不再参与缩放 | 不涉及消息层 | 中:输入/焦点/IME 路由要理清,但**不需要换掉 winit** |

第四条需要特别说明:`winit 0.30` 的 `WindowAttributes::with_parent_window`(unsafe,Windows 下建 `WS_CHILD` 子窗口)现成可用,`create_surface` 对子窗口一样成立,`wgpu` 与 `softbuffer` 都不用改。父窗口负责标签栏(纯布局,不 reflow,重绘极快),子窗口负责终端内容(尺寸不变,于是不被缩放),reflow 延后到拖动结束 —— 这正是 Windows Terminal 用 XAML 岛做到的效果,而 GDI 时代的终端天然就是这个模型。

**所以 E(换掉 winit)不是解决抖动的正确买法。真正该买的是"换合成模型"(C),而它不需要付 E 的价钱。**

不过这条有个必须诚实标注的软肋:**它依赖"DWM 对子窗口的独立合成表面不参与父窗口缩放"这一行为**,而这一点本文没有验到源码级证据(Windows Terminal 用 XAML 岛的效果是可观察的旁证,但那是 DirectComposition 视觉树,不等于任意子 HWND + DXGI swapchain)。**落地前应先写 30 行 demo 验证**:主窗口 + 一个子 HWND 挂 swapchain,拖主窗口右边框,抓帧看子窗口里的文字跨度变不变。

### 7.2 更本质的一条:拉伸是 DXGI 的一个枚举值

上面所有讨论都绕着一个词——"拉伸"。它不是 DWM 的某种必然行为,而是 `IDXGIFactory2::CreateSwapChainForHwnd` 时传进去的 `DXGI_SCALING`:

| 值 | 语义(MSDN 原文要点) |
|---|---|
| `DXGI_SCALING_STRETCH`(0) | 后缓冲内容**缩放**到呈现目标尺寸;这是默认 |
| `DXGI_SCALING_NONE`(1) | 后缓冲**不做任何缩放**,左上角对齐;目标区超出的部分填 `SetBackgroundColor` 的背景色 |
| `DXGI_SCALING_ASPECT_RATIO_STRETCH`(2) | 保比例缩放(仅 Windows Phone / 部分场景) |

而 **`wgpu-hal 24.0.4` 把这一项写死成 `STRETCH`**(`src/dx12/mod.rs:1135`:`Scaling: Dxgi::DXGI_SCALING_STRETCH`),`wgpu::SurfaceConfiguration` 没有对应字段。

也就是说:**四轮时间里被反复优化掉的那 7~8ms,本质是在跟一个不可达的枚举值搏斗。** 如果把它换成 `NONE`,拖动时窗口变大、旧 buffer 只是**贴在左上角不缩放**,多出来的区域用背景色填一帧——文字不发生形变,`T` 立刻就不再是"肉眼可见的形变",而退化成"右下角一条背景色窄边"。这是 GDI 时代终端的天然语义,也是 ConEmu / mintty / PuTTY 从来不抖的真正原因:它们根本不走 DXGI 的缩放路径。

需要注意三个前提:

1. MSDN 写明 `NONE` **只保证 `DXGI_SWAP_EFFECT_FLIP_SEQUENTIAL`**;wgpu 用的是 `FLIP_DISCARD`,能否生效需要实测(驱动层面通常支持,但不能只靠推测)。
2. wgpu 不暴露 `SetBackgroundColor`,新区域的填充色不可控(可能是黑色)——但那只是一帧的窄边,比文字形变更可接受;若不可接受,可在 `NONE` 基础上叠 A 方案(拖动中按旧尺寸出帧,连窄边都没有)。
3. 落地代价:fork `wgpu-hal` 改一行,用 `[patch.crates-io]` 挂本地路径;或者向 wgpu 上游提一个 `swapchain_scaling` 配置项。风险是长期跟上游同步一个很大的 crate。

**优先级应该调整:`NONE` 实验(约半天,含 fork 与抓帧对照)排在 A 之前**,因为它是唯一能从"定义上"消掉形变、且不引入第二个窗口的做法。若 `NONE` 被 `FLIP_DISCARD` 拒绝,再退回 A(应用层),子 HWND 作为第三条备选。

---

## 8. 一句话总结

其它终端在 resize 时改的是**视口**,我们在 resize 时改的是**排版**;视口变化可以立刻出示,排版变化必须等算完。DWM 不会等,它只会把上一张图拉长 —— 于是每拉一点,就抖一次。

四轮修的是"让它早 1 毫秒",而真正该修的是"让它不必早"。
